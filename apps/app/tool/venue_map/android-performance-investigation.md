同じ日に、初回修正に続いて以下を実施した。歩行・カメラ・会場形状・影・描画解像度の設定は維持している。

### メモリーと画質

3D用の床画像は縦横を半分にし、RGBA8の2枚とmipmapを合わせて計算上約14.6MiBに制限する。
同じ原寸のRGBA8なら約58.5MiBになるため、その4分の1に抑えている。
修正前のETC2では約7.3MiBだったので、圧縮状態との比較では約7.3MiB増えるトレードオフがある。
これらは床テクスチャの画素データの容量で、アプリ全体のPSSやドライバーの一時メモリーの実測ではない。

床画像には文字を焼き込んでおらず、ラベル・看板の解像度は変更しない。
両テーマの実画像をGPUへ読み込むテストで、1774 × 810、mipmapあり、2枚の合計15MiB未満を検証した。
実機での長時間利用・発熱・FPSは引き続き未計測であり、今回の修正で全端末の性能を保証するものではない。

## 修正前の調査結論

Androidエミュレーターで、3Dの初回表示に約30秒を要する問題を再現した。
ソフトウェア描画では30秒で読み込みエラーになり、ホストGPUを使用したreleaseビルドでも、20秒時点では読み込み中、31秒時点でようやく3D表示を確認できた。
現状を「パフォーマンス上の問題なし」とは判断できない。

大きな原因は、床画像2枚を端末向けのETC2形式に実行時変換する処理だった。
同じ画像でこの変換を回避すると、床画像の読み込み合計は33.347秒から0.416秒に短縮した。
だしゅまるモデルや会場形状の軽量化より、テクスチャの読み込み経路を優先して改善する根拠が得られた。

過去の報告は「エミュレーターでリリース確認中のローカル実行」まで確認できたが、当時のバージョン・GPU設定・ログは不明。
今回の再現と過去の報告が完全に同一の条件・原因だったとは断定しない。
この事前調査の段階ではアプリ本体を修正せず、上記の修正は調査後に実施した。

## 30秒の内訳

アプリの実際の`VenueWalkScene.load()`に、段階ごとの時刻ログだけを加えたprofileビルドを使用した。
次の値はソフトウェア描画条件における1回の測定で、処理開始からの累積時間である。

| 完了した処理                      | 累積時間 |
| --------------------------------- | -------: |
| Flutter Sceneの静的リソース初期化 |  0.146秒 |
| 会場JSON読み込み                  |  0.146秒 |
| だしゅまるモデル読み込み          |  0.230秒 |
| ライト用床テクスチャ読み込み      | 18.546秒 |
| アプリのタイムアウト              |   約30秒 |
| ダーク用床テクスチャ読み込み      | 33.577秒 |

床画像2枚だけで33.347秒を消費した。タイムアウト後にも変換処理は継続しており、永続的な初期化停止ではなかった。
看板・会場装飾の生成に進む前に30秒を超えている。
モデルを使わない初期化だけの最小構成でも、シェーダー・マテリアル・SMAA・Androidのmip sampling probeは合計約0.47秒で完了した。

関連する処理:

- `lib/feature/venue_map/data/venue_walk_scene.dart:139`から、ライト・ダークの床画像を順番に読み込む。
- `lib/feature/venue_map/ui/widget/venue_walk_view.dart:113`で、シーン読み込み全体に30秒の制限を設定する。
- Flutter Scene 0.23.0の`texture_registry.dart` → `compressed_texture.dart`で、対応GPU形式を選び、`compute()`の別isolateで変換する。
- この端末条件では`transcode_etc2.dart`の変換経路が選ばれる。別isolateのためローディング表示は動き続けるが、変換時間自体は短縮されない。

床素材は各3548 × 1620ピクセル、10 mip levels、各約48万個の4 × 4ブロック。
`.fstex`のファイルサイズは各約54KBと小さいが、展開・変換する画素数は大きい。
build hookによる事前変換後にも、実行端末向けの形式変換が残っている。

## 原因を確かめた比較実験

同じエミュレーター・画像・モデル・profileビルドで、調査用コピーだけにRGBA8へ展開する設定を加えた。
Flutter Scene内部の`compressionFamilyPreference`を空にし、ETC2への変換を回避した。
解像度やmip数、看板、壁、影の設定は変更していない。

| 指標            |     通常のETC2経路 | 調査用RGBA8経路 |
| --------------- | -----------------: | --------------: |
| ライト用床画像  |           18.316秒 |         0.160秒 |
| ダーク用床画像  |           15.031秒 |         0.256秒 |
| 床画像2枚の合計 |           33.347秒 |         0.416秒 |
| シーン構築      | 30秒でタイムアウト |   4.228秒で完了 |
| 3Dの実画面      |         エラー表示 |        表示成功 |

4.228秒はシーン構築完了までの時間であり、表示言語の更新や最初の描画完了までの時間ではない。
ソフトウェア描画では初回描画にも待ちがあり、スクリーンショット要求自体にも遅延が生じた。
「3Dが4.228秒で画面に表示された」という意味ではない。

RGBA8は原因を切り分けるための実験で、恒久策として採用していない。
床2枚のRGBA8データはmip込みで計算上約58.5MiBとなり、GPUメモリーとのトレードオフがある。

### 表示後の参考計測

表示できたRGBA8比較用ビルドについて、ソフトウェア描画・入口で停止中のFlutterタイムラインを10秒間取得した。

| 指標                                             |                  値 |
| ------------------------------------------------ | ------------------: |
| フレーム開始の間隔から求めた生成頻度             |    約4.9フレーム/秒 |
| UI側の`Frame`時間の中央値 / 95パーセンタイル     |    4.924 / 10.791ms |
| `GPURasterizer::Draw`の中央値 / 95パーセンタイル | 189.176 / 322.924ms |

UI側47サンプル、Raster側46個の完了サンプル。95パーセンタイルは昇順配列の`floor((n - 1) * 0.95)`の値。
この条件では描画側の負荷が大きい。これはGPU処理の完了時間そのものや、実機・通常release版のFPSを示す値ではない。
録画ファイルのエンコードFPSもアプリのFPSの代用にはしていない。

## 次に優先する対応

1. **床テクスチャの実行時ETC2変換を回避・削減する。** ビルド時に端末用形式を用意する方法、PNG等からの読み込み、解像度の見直しを比較する。今回のRGBA8実験は効果の証拠として使い、メモリーと画質を含めて方式を決める。
2. **初回に必要なテーマの床画像を優先する。** 現状はライトテーマでもダーク用画像の変換完了を待つ。非選択テーマを遅延読み込みする場合は、テーマ変更時の待ち・リソース寿命も確認する。
3. **初回表示と表示後を別々に計測する。** 読み込みの各段階、言語更新、最初の3D描画完了、通常歩行中のフレーム時間を分ける。エミュレーターのGPU設定も記録する。
4. **実機のprofile / releaseで再確認する。** ETC2だけでなくASTC対応端末も含め、初回・再起動・2D/3D往復、メモリー、発熱を確認する。

30秒制限の延長だけでは、初回の長い待ちや変換負荷は解消しない。
既存のWeb側の描画最適化は有効な別の対策だが、今回のネイティブの画像変換時間を検証したものではない。

## 再現手順と記録

SDKの`emulator`コマンドで、同じAVDを保存なしで起動した。

```sh
emulator -avd Pixel_9 -read-only -no-snapshot-save \
  -no-boot-anim -no-audio -no-window -gpu auto
```

ホストGPUとの比較では`-gpu host`だけを変更する。
AVDの設定名だけでなく、エミュレーターの起動ログとFlutterの`Using the Impeller rendering backend`、`texture compression support`を確認する。
[Android EmulatorのGPU設定](https://developer.android.com/studio/run/emulator-acceleration)

調査用コピーの`apps/app`でビルドし、ADBでインストール・起動した。

```sh
fvm flutter build apk --profile --target-platform android-arm64 --no-pub \
  --dart-define-from-file=environments/.env.dev

# releaseは隔離したコピー内にローカル検証用の署名設定を用意して実行
fvm flutter build apk --release --target-platform android-arm64 --no-pub \
  --dart-define-from-file=environments/.env.dev --dart-define=APP_ID_SUFFIX=.perf
```

今回の再現用スクリプトは、表示済みの2D画面から3Dをタップして31秒間の画面とlogcatを記録し、3Dが準備できなければ終了コード1を返す。

```sh
python3 /tmp/flutterkaigi-android-investigation/probe.py release-first-3d \
  --tap 944 342 --package jp.flutterkaigi.conf2026.perf --assert-ready
```

ソフトウェア描画のreleaseでは次の結果になり、ホストGPUでは同じAPKで準備完了を確認した。

調査用コピー、スクリプト、画面・動画・ログ・タイムラインはローカルの`/tmp/flutterkaigi-android-investigation/`に保存した。
