# チェックイン後のチーム選択への変更設計

## 依頼と現状

現状は参加表明後、運営が「チーム選択を開始」すると、参加者は A〜T のチームを選択できる。チーム選択は自己申告のため、会場にいない参加者もテーブルを選べてしまい、着席人数とダッシュボードの照合・個別取消の手間が大きい。

依頼された形は次のとおり。

- 参加登録は現状どおり。
- 参加登録の終了後からチェックインできる。
- チェックインは QR または6桁の参加コードで行う。
- チェックイン後にチーム（卓）を選べる。

登録枠、前後半の重複防止、運営操作の再送保証、アカウント削除保護、未選択者の一括取消、初出題時のチーム確定、回答・採点は維持する。

## 提案

1. 受付窓口は既存の `teamSelectionStatus`（`notStarted` / `open` / `closed`）をそのまま使い、意味を「チェックイン・チーム選択の受付」に広げる。フィールド名は変えず、画面の文言だけ「チェックイン」に改める。フィールドを分けると「チェックインは受付中だが選択は終了」などの組合せが増え、運用上の意味がないため。
2. 初回の開始（`notStarted → open`）は大会が `entryClosed` のときだけ許可する。これが「参加登録終了後からチェックイン可能」の正本となる。終了後の再開（`closed → open`）は、当日枠のため受付を再開した `registration` でも許可する。終了（`closeTeamSelection`）は従来どおり `registration` / `entryClosed` で許可する。
3. 参加コードは大会ごとに1つの6桁数字とし、`quizEvents/{eventId}/secret/checkIn` に `{ code, updatedAt }` で保存する。初回開始の操作と同じトランザクションで、未発行なら発行する。再開ではコードを保持し、投影中の QR を無効にしない。漏えい時のため運営操作 `regenerateCheckInCode` を追加する。初出題前（`registration` / `entryClosed`）で、受付開始後のみ許可する。チェックイン済みの参加者は再発行の影響を受けない。`secret/*` は既存ルールで管理者のみ読み取りできる。
4. 参加記録 `participants/{uid}` に `checkedInAt`（Timestamp、未チェックインは欠落または null）を追加する。書き込みはサーバーのみ。
5. Callable `checkInQuizParticipant(eventId, code)` を追加する。
   - 非匿名アカウント、`code` が6桁数字であることを検証する。
   - 登録と同じく、トランザクション内で `quizParticipation/{uid}` の `accountDeleted` を確認し、Auth アカウントが有効であることを確かめる。削除処理と競合したリクエストが試行記録を再作成しないようにする。
   - 大会・本人の参加記録・`secret/checkIn`・試行記録を単一トランザクションで読む。
   - 参加記録がなければ拒否する。チェックイン済みなら、受付終了後でもコードを照合せず成功を返す（応答喪失からの再送を成功させる）。
   - 大会が `registration` / `entryClosed` かつ受付が `open` でなければ拒否する。
   - 誤りは `quizEvents/{eventId}/checkInAttempts/{uid}` に1分あたり5回まで記録し、超過時は `resource-exhausted`（`reason: rate-limited`）、誤りは `permission-denied`（`reason: wrong-code`）で返す。旧 `entryAttempts` と同じく、照合の前に上限を判定し、誤りの試行記録をコミットしてからエラーを返す。
   - 一致すれば `checkedInAt` を書き、試行記録を削除する。
6. `selectQuizTeam` に「本人がチェックイン済み」の条件を追加する（`failed-precondition`、`reason: check-in-required`）。同じチームの再送は従来どおり先に無変更で成功させる。
7. 未選択者の一括取消・個別取消は従来どおり。対象には未チェックイン者も含まれる（未チェックイン者は必ず未選択のため）。取消時は `checkInAttempts/{uid}` も削除する。初出題の条件（受付終了、全員が A〜T 選択済み）も従来どおり。選択にはチェックインが必須なので、選択済みはチェックイン済みを意味する。
8. QR の内容は応援LTの出席 QR と同じ形にそろえ、`<アプリの Web オリジン>/account/quiz/<eventId>/check-in/<6桁>` とする。オリジンは応援LTと同じく操作対象の Firebase プロジェクトから決め（本番 `https://2026-app.flutterkaigi.jp`、STG は STG のドメイン）、ローカルのエミュレーターでは6桁のコードだけを QR にする。
   - アプリ内の読み取りは、許可したオリジンでパスが `/account/quiz/<表示中の eventId>/check-in/<6桁>` の URL、または6桁のコードだけを受け付ける。別の回の QR は「別の回の QR です」と表示する。
   - OS のカメラで読んだ場合は、新しいルート `/account/quiz/:eventId/check-in/:code` でクイズ画面を開く。チェックイン画面はコードを入力済みの状態で表示し、自動で1回だけ送信する。送信済みの記録はページで持ち、サインインや画面の切り替えで送り直さない（誤ったコードのリンク1つで試行上限に達しないようにする）。
   - 未サインインで開いた場合も、クイズ画面内でサインインできるようにし（応援LTと同じ `SignInCard`）、サインイン後に参加記録を読み込んでから1回だけ送信する。
9. 参加者アプリの画面遷移。
   - 受付が `notStarted` の間は待機画面に「参加登録の終了後、会場でチェックインを開始します」と表示する。
   - 受付開始後、未チェックインなら「チェックイン」画面を表示する。6桁入力欄、送信ボタン、「QR を読み取る」ボタン（カメラ画面を開く）を置く。受付終了後の未チェックイン者には、受付が終了した旨とスタッフへの声かけを案内する。
   - チェックイン済みならチーム選択画面を表示する（現状の画面）。
   - 自動再送はせず、送信中はボタンを無効化し、Firestore の `checkedInAt` を表示の正とする。
10. ダッシュボードのコンソール。
    - 「チェックイン・チーム選択」カードに、状態、参加表明数、チェックイン済み数、チーム選択済み数、未選択数を表示する。
    - 受付開始後は参加コード（大きく表示）と QR、「コードを再発行」ボタンを表示する。
    - 開始ボタンは `entryClosed` 以外では初回開始を無効化し、理由を表示する。
    - 参加者一覧は「未チェックイン / チェックイン済み・未選択 / チーム X」を表示する。
11. 投影画面は受付 `open` の間、QR と6桁コードを大きく表示する。80人に同時に配るには投影が最も早いため。STG/本番切替経路（管理用 Callable の `quizConsole` / `quizProjection` 画面データ）にも `checkInCode` を追加する。投影画面を配信映像から外すことを必須の運用とし、RUNBOOK に明記する。漏えいが疑われる場合は、露出を止めてから再発行し、その間にチェックインした疑わしい参加者は本人の画面で確認して個別に取り消す。
12. Firestore Rules / スキーマ。`checkInAttempts` は読み書き禁止。参加者スキーマに `checkedInAt` を追加する。Auth 削除時の非公開データ削除と、STG→本番反映の取消前検査の対象に `checkInAttempts` を加える。STG→本番反映は `secret/checkIn` をコピーしない。

## 変更範囲

- Functions: `quiz_service.ts`（チェックイン、選択条件、運営操作）、`quiz.ts`（Callable 登録）、`event_admin_service.ts`（画面データの `checkInCode`）、`auth_user_data.ts`、`quiz_promotion_service.ts`、テスト。
- Firestore Rules、参加者の JSON Schema。
- data パッケージ: `QuizParticipant.checkedInAt`、参加者リポジトリの `checkIn`、運営リポジトリの `regenerateCheckInCode`、大会リポジトリのコード購読、QR 内容の生成・解析。
- 参加者アプリ: チェックイン画面、QR 読み取り、ルートのクエリ、文言（日英）。
- dashboard: コンソール、投影画面、STG/本番切替用リポジトリ。
- `DESIGN.md` / `RUNBOOK.md`。

## 配布と切替

Functions と Rules → ダッシュボード → 新アプリの配布 → Remote Config の `force_update.minimum_version` 引き上げの順に反映する。旧アプリはチェックイン画面を持たず、選択が `check-in-required` で失敗するため、チェックイン開始前に強制更新へ誘導する。本作業では本番デプロイ・ストア公開・Remote Config の変更は行わない。

Web 版は強制更新の対象外のため、Web の新版を配布し、開いたままの旧タブは再読込してもらう。旧画面は `check-in-required` を汎用エラーとして表示するため、切替後に旧タブで選択を試みた場合の表示も確認する。

デプロイ時点で既にチーム選択を開始（`open` / `closed`）している大会では、コードが未発行で、チェックインなしの選択済み参加者が残る。切替前に該当する大会がないことを確認する。残っていた場合は「コードを再発行」でコードを発行し（未発行でも発行できるようにする）、チェックインなしの選択済み参加者を個別に取り消す。

## 当日の操作

- 前半15:30に参加受付を終了し、チェックインを開始する。投影画面に QR とコードを表示する。
- 参加者は着席後、アプリでチェックインし、スタッフに案内されたチームを選ぶ。
- 15:40に未選択者（未チェックインを含む）を確認して一括取消する。
- 当日枠を案内して受付を再開する。当日参加者は参加表明後、そのままチェックインとチーム選択を行う。
- 出題前に参加受付とチェックインを終了し、未選択者が残っていないことを確認する。

## 来場確認の扱い

コードは会場の投影でのみ配るため、会場外の参加者がチームを選ぶには会場内の誰かからコードを受け取る必要がある。物理的な来場証明ではないが、意図しない会場外の選択はなくなる。コードが会場外に広まった疑いがあれば再発行する。運営は引き続き着席人数とチーム別一覧を照合する。

## 検証

Functions の単体・エミュレーターテストで、チェックインの認可・コード照合・試行制限・再送・受付状態、初回開始の `entryClosed` 条件、コードの発行・保持・再発行、未チェックインの選択拒否、取消時の試行記録削除を確認する。Dart のテストで QR 内容の解析、チェックイン画面の入力・送信・エラー・終了表示、チェックイン後のチーム選択、ダッシュボードのコード表示と開始条件を確認する。
