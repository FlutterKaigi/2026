# クイズ大会 当日の運用手順

## 事前準備

1. Functions・Firestore Rules → ダッシュボード → 新アプリの iOS / Android 配布の順に反映する。
   配布した版を Remote Config `force_update.minimum_version` の両OSに指定し、旧版を更新へ誘導する。
   版番号は実際の配布時に確定する。旧版はチーム選択できないため、受付開始前に更新を確認する。
   ローカル検証では Functions を含むエミュレーターを起動する。
2. 運営用の確認済み `@flutterkaigi.jp` アカウントをダッシュボード接続先の `admins` に登録する。
   予備PCでもログインを確認する。イベント画面の「操作環境」で STG / 本番を選ぶ。
   環境切替でアカウントを変える必要はない。本番進行前に「本番のイベントを操作中」の表示を確認する。
3. STG に前半・後半の大会を作り、問題・正解・解説を登録する。動作確認後、開催する大会を1件ずつ
   「本番へ反映」から本番の下書きとして作成する。スポンサーを先に本番へ反映しておく。
   本番に参加者・回答・チーム選択・進行状態はコピーされない。本番側で内容を開き直して確認してから公開する。
4. 定員3〜80人、A〜T の20テーブルを準備する。8問を各3分＋読み上げ各1分で実施すると32分かかる。
   説明・移動・表彰を含めて持ち時間に収まるよう問題数・制限時間を確定する。
5. STGで通しリハーサルを行う。本番での練習登録も前後半の参加権を消費する。
   本番で誤登録した場合は初出題前に参加取消する。
6. テーブルには数字の選択肢と混ざらないよう A〜T の表示を用意する。
   全体通信障害時に紙回答へ切り替えるか中止するかを事前に決め、記録用紙を用意する。

## 参加表明・当日のチーム選択

前半戦の時刻を示す。後半戦は1時間後ろへずらす。時刻による自動切替はなく、運営が操作する。

1. 開催前に大会を公開し「参加登録を開始」を押す。参加者はサインインして前半・後半のどちらかに参加表明する。
2. Day 2 15:30 に参加受付を終了し「チーム選択を開始」を押す。旧方式の割当があれば初回開始時に解除される。
3. スタッフが来場者をテーブルへ割り当てる。参加者は着席してからアプリで A〜T を選び「このチームに決定」を押す。
4. 15:40 に「未選択者のみ表示」で来場していない参加者を確認する。「未選択者を一括取消」で枠を解放し、取消件数を確認する。
5. 「受付を再開」を押し、空き枠に当日参加者を案内する。参加表明 → スタッフのテーブル指定 → 本人のチーム選択の順に進める。選択済みの所属は保持される。
6. 参加受付を再び終了する。テーブルの実人数と管理画面のチーム別一覧を照合する。
   チーム選択は自己申告で会場外からもできる。相違があれば表示名・UID・本人画面を確認し、初出題前に個別取消する。
7. 「チーム選択を終了」を押す。未選択者が残っていないことを確認し、15:40〜15:45 に進行方法を説明する。
8. 15:45 から問題を表示する。初出題でメンバーのいるチームが確定する。以降は登録・取消・チーム変更ができない。

チーム選択は初出題前なら再開できる。前半・後半への重複登録は禁止され、取消済みの人は空き枠があれば再登録できる。
一括取消は、参加受付を閉じ、チーム選択を開始した後にだけ有効になる。

## 間違った大会を本番へ反映した場合

1. 本番側で対象を確認し、参加受付を開始する前に「反映を取り消す」を押す。
   公開済みでも受付準備・開始前なら非公開にして取り消せる。内容と操作履歴は保持される。
2. STG の正しい大会を開いて反映し直す。取り消したコピーと別 ID で作られ、他の本番大会は変更されない。
3. 参加受付・回答開始後は取り消せない。受付中なら新規参加受付を終了し、既存の参加者・回答を保持したまま
   運営で対応を決める。自動的な上書き・削除・初期化で戻す機能は設けていない。

同じ大会が反映済みの場合は本番の既存大会を開き、二重に作成しない。再試行で STG の動作確認データや
古い定義を上書きすることもない。開催前に STG の修正を反映し直す場合は、既存コピーを取り消してから反映する。

## 出題・回答・結果

1. 「投影画面」を別ウィンドウで開く。URLの `environment` と投影画面上部の環境表示を確認する。
   プロジェクターに管理画面を映さない。
2. 「問題を表示」を押して読み上げる。この間は回答できず、タイマーも進まない。
3. 読み上げ後に「回答開始」を押す。ここから設定した制限時間を数える。
4. チーム内の誰でも回答を変更できる。最後にサーバーが受理した選択肢が最終回答となる。
   参加者には「受理済み」を確認してもらい、送信中・受理未確認のままなら別の端末でも確認する。
5. 締切後に「締切」「正解発表」を操作する。正解発表前なら30秒延長して再受付できる。
   延長しても既存の回答は残る。通信障害時の延長は全チームへ告知する。
6. 正解発表後に次問へ進む。最後の問題の正解発表が終わったら大会を終了する。
   時間超過時は未出題の問題を残して終了できる。確認画面で残り問題数を確認し、出題済み分で集計する。
7. 同率順位は全チーム表示される。入賞3チームへの絞り込みは会場でじゃんけん等を行う。

## 障害時

| 症状 | 対応 |
| --- | --- |
| チームを選べない | 新版への更新、参加表明、選択受付の状態を確認。取消後は再登録が必要 |
| 初出題できない | 参加受付・チーム選択を終了し、未選択者を確認して取消または選択再開 |
| 満員または別大会に登録済み | 管理画面で登録一覧を確認。必要なら初出題前に誤登録を取消 |
| 送信結果が確認できない | 通信回復後にチームの回答を確認し、必要なら期限内に再送。運営判断で正解発表前に延長 |
| 時計の同期に失敗 | 通信を確認して再試行。端末時計を変更してもサーバー期限は変わらない |
| 運営操作がタイムアウト | まず状態・期限・チームを確認。同じ画面から再試行する |
| 運営PC故障 | 予備PCで状態を確認して継続。延長・チーム選択が反映済みか確認してから操作 |
| 全体通信障害 | 決めておいた紙回答・中断手順を実施。未受理の回答を受理済みとして扱わない |

運営操作の重複防止IDは同じ管理画面での再試行に引き継がれる。一括取消は毎回現在の未選択者を再判定する。
画面再読込・別PCでは新しい操作になるため、すでに反映された結果を確認してから押す。
通信エラー後に受付の終了・再開を往復すると、再押下が前回の結果を返すだけで状態が変わらない場合がある。
操作後の状態を確認し、必要な状態になっていなければもう一度操作する。
正解発表後の問題訂正、開始後の参加者追加・チーム変更は提供しない。
誤出題はその問題の扱いを運営が判断し、通常運用でFirestoreを直接編集しない。

## リハーサルで確認すること

- 80人の定員境界、前後半の重複参加、コードなし登録、未選択者取消後の枠解放と再受付。
- 複数運営端末からの同時操作、古い問題編集画面での保存拒否。
- 読み上げ→開始→締切→延長→正解発表→終了の通し進行。
- チーム複数端末での回答変更、締切直前の通信断と再接続、アプリ再起動。
- 端末時計がずれた状態、バックグラウンド復帰時の残り時間。
- 同率順位、A〜T の選択と変更、同時選択・取消の競合、投影画面に受付コード・未公開正解が出ないこと。
- 実機のApp Check、会場Wi-Fi、予備PC、司会を含む所要時間。
