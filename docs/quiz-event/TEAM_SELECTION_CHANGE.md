# 参加表明・会場でのチーム選択への変更設計

## 依頼と現状

参加者は前半戦または後半戦の大会を選んで参加表明する。6桁コードと追加の名前入力は不要とする。会場では運営が座席を割り当て、参加者自身が A〜T の20チームから座ったテーブルを選ぶ。チーム選択済みを来場確認として扱い、未選択の参加者を運営がキャンセルして当日参加者の枠を空ける。

現状はコード照合後に登録し、受付終了後に3〜5人へ自動編成する。受付再開・参加取消で全チームを解除する実装がある。登録枠、前後半の重複防止、運営操作の再送保証、アカウント削除保護、回答・採点は維持する。

## 提案

1. 大会の `status` は維持し、サーバーが操作する `teamSelectionStatus` を追加する。値は `notStarted` / `open` / `closed`、未保存は `notStarted`。参加受付の開始・終了とチーム選択の開始・終了を独立させる。自動時刻切替は導入しない。
2. `registerQuizParticipant` は受付コードなしで登録する。公開表示名は本人が公開保存した `users/{uid}.displayName` をサーバーが読み、名前がない場合は「参加者」を使う。Auth のアカウント名を公開表示名に使わない。前後の空白を除去し20書記素へ切り詰め、名前の長さを理由に登録を拒否しない。旧クライアントが明示的に送る大会用 `displayName` は同じ正規化を通して受け入れる。名前入力欄をなくし、受付回の確認と参加表明ボタンだけにする。定員3〜80人、認証済みの非匿名アカウント、前後半の重複参加禁止を維持する。古いクライアントが送る `entryCode` は無視する。
3. 運営の `openTeamSelection` で A〜T の20チームを選択可能にする。`openTeamSelection` / `closeTeamSelection` は `registration` または `entryClosed` でのみ許可する。初出題前の所属の正本は参加者の `teamId` のみとし、チーム文書はまだ作らない。再開は選択済みの所属を保持する。旧自動編成がある未出題大会は、初回開始の確認画面で旧割当の解除を明示し、既存登録者を保持して会場で選び直してもらう。出題済み大会は変更しない。
4. `selectQuizTeam(eventId, teamId, expectedTeamId)` を追加する。本人の参加記録、イベントが `registration` または `entryClosed`、選択受付が `open`、チームIDが A〜T であることを検証する。イベントと本人の参加記録を単一トランザクションで読み、本人の `teamId` だけを更新する。受付中は選び直せる。同じチームの再送は所属を検証して無変更で成功し、締切後も応答喪失から回復できる。変更前の所属が `expectedTeamId` と一致しなければ拒否する。アプリは自動再送せず、送信中は選択ボタンを無効化し、Firestore の所属購読値を表示の正とする。チーム人数はスタッフが座席で調整するため、新たな人数上限は設けない。
5. チーム未選択は `participant.teamId` フィールドの欠落または null とする。一括取消と初出題では参加者全件（80件以内）をトランザクションで読み、コードで判定する。ダッシュボードは参加表明数、選択済み数、未選択数、各チーム人数と一覧を表示する。個別キャンセルは対象の所属だけ外し、他のチームを保持する。未選択者の一括キャンセルを確認付きで追加し、実行時点で再確認する。選択や登録との競合はトランザクションで直列化する。一括キャンセルは `entryClosed` かつ選択状態 `open` / `closed` でのみ UI とサーバーの両方で許可し、`notStarted` では禁止する。参加者、予約枠、`participantAccounts`、`entryClaims` を削除し、全体の参加記録は同じ大会を指し `accountDeleted` でない場合だけ削除する。削除済みアカウントの墓標は保持する。取消後は同じ回・別の回への登録が可能になる。一括取消は押下ごとに新しい操作IDを用い、実際の取消件数を返して表示する。キャンセル後に受付を再開して当日参加者を登録する。
6. 受付再開は全チームを保持する。最初の出題には参加受付終了、チーム選択終了、1名以上の選択済み参加者、全参加者が A〜T のいずれかを選択済みであることを要求する。最初の `presentQuestion` または直接の `openQuestion` と同じトランザクションで、参加者からメンバーのいるチームだけを確定作成する。ID・表示名は A〜T、`tableNumber` は A=1〜T=20、`memberUids` / `members` は参加記録から生成する。未選択者が残ると開始できず、運営にキャンセルを案内する。出題開始後は選択・変更・登録・取消を禁止する。
7. 空チームは選択肢として表示するが、初出題でチーム文書を作らないため、回答ドキュメント、回答数の母数、ランキング、入賞、スポンサー賞には含まれない。開始前のチーム表示・人数集計は参加者から作り、開始後の回答・採点は既存の確定チームを使用する。全体表示はチーム A などアルファベットを主体とし、数字のテーブル表示をなくす。回答選択肢は参加者画面・投影画面とも1〜4に統一し、チーム名と区別する。既存の進行中・終了大会の名前と得点はそのまま表示する。
8. 自動編成、名前プール編集、受付コード発行の運営導線を削除する。旧コード照合や自動編成のサーバー操作も停止する。旧フィールド・非公開履歴は必要な互換読取やアカウント削除処理のため残してよいが、新しい大会の受付要件にしない。
9. Firestoreの直接書込み禁止を維持する。新しい選択状態と固定チーム名は管理者の直接編集でも変更不可。既存の `teams.name` の直接変更許可を撤去する。選択状態は設定保存の許可リスト `eventDefinition` に含めず、新規作成時もフィールドを省略する。STGから本番への反映は選択・所属状態をコピーしない。

## 変更範囲

- Functions の登録・選択・運営操作・回答作成・採点と、Firestore Rules / JSON Schema。
- data パッケージの大会モデル、参加者・運営リポジトリ。
- 参加者アプリの登録・チーム選択・チーム表示・ランキング、日本語と英語の文言。
- dashboard の作成・進行・投影画面、および `core/event_environment/event_admin_repositories.dart` の STG/本番切替用実装。
- `event_admin_service.ts` の管理操作と読取。`renameTeam`、`updateTeamNamePool`、受付コードの読取も停止する。`openRegistration` のコード必須条件、`regenerateEntryCode` 操作、作成時のコード自動発行を撤去する。
- 既存テストを新仕様へ更新し、`DESIGN.md` / `RUNBOOK.md`・seed データも合わせる。

## 配布と切替

Functions と Rules → ダッシュボード → 新アプリの iOS / Android 配布 → Remote Config の `force_update.minimum_version` を配布済み新版へ引き上げる順に反映する。コード入力が必要でチーム選択のない旧版は、参加受付開始前に強制更新へ誘導する。実際に配布する版番号はリリース時に確定し、両OSで更新と選択ができることを確認してから受付を開始する。本作業では本番デプロイ・ストア公開・Remote Config の変更は行わない。

## 当日の操作

- 事前に前半・後半の大会を作成、公開し、参加受付を開始する。
- 前半15:30に参加受付を終了し、チーム選択を開始する。後半は1時間後。
- 15:40に未選択者を確認してキャンセルする。選択済みの参加者と所属は保持する。
- 当日枠を案内して参加受付を再開する。参加表明後にスタッフがテーブルを指定し、本人がチームを選ぶ。
- 説明・出題前に参加受付とチーム選択を終了し、未選択者が残っていないことを確認する。

## 来場確認の扱い

チーム選択は参加者の自己申告であり、端末の物理的な来場証明にはならない。依頼された運用に沿って追加コードや位置情報は要求しない。アプリには「スタッフに案内されたテーブルに着席してから選択」と案内する。運営はテーブルの実人数とダッシュボードのメンバー一覧を照合し、不一致があれば本人のアプリ画面で確認して初出題前に個別取消する。

## 検証

Functions の単体・エミュレーターテストでコードなし登録、80人定員と二重参加、選択の認可・変更・再送・同時選択、未選択取消との競合、枠解放、初出題ガード、空チーム除外、旧大会からの初回準備、旧コードが不要であることを確認する。Dart のリポジトリ・ウィジェットテストで登録に入力不要、選択中・成功・エラー・締切表示、運営の取消と受付再開、回答・投影・結果表示を確認する。変更後にClaude Opus 5.5 maxで実装レビューを行う。
