# Venue subtitles architecture

## ステータス

この文書はFlutterKaigi向け正面スクリーン字幕の**技術試作**を記述します。本番採用は未承認です。DroidKaigi向け試験後のフォローアップをチェックポイントとし、実会場試験と理事・運営・会場・制作・収録担当の合意を経てGo／No-Goを決めます。

来場者アプリ内字幕は「正面スクリーンが不採用・停止しても利用できる」必須の独立フォールバックです。アプリチームが並行開発を継続し、このブランチでは実装しません。正面スクリーン方式の進捗を理由にアプリ側の準備を止めないことを前提とします。

## 目的

正面スクリーンへ翻訳字幕を表示しつつ、字幕システムの障害が登壇者映像を止めない構成を試します。来場者アプリ向け字幕は並行開発を必須とし、正面スクリーンの本線からクラウド依存を分離します。

このブランチの実装範囲は、翻訳済み字幕イベントの受信・順序制御・OBS合成用表示です。PA音声を扱うSTT・翻訳producer、翻訳サービス、用語集は未選定・未実装のブロッキング項目です。下図の先頭は本番候補全体を示し、現時点で実行可能なのは`Caption relay`以降です。

## 信号とデータの流れ

```text
PA／マイク音声 ─→ STT・翻訳プロセス
                         │ localhost HTTP
                         ▼
                  Caption relay (memory only)
                         │ localhost WebSocket
                         ▼
登壇者PC HDMI ─→ OBS + Flutter Web overlay ─→ 合成HDMI ─→ projector
       │
       └──────── 物理バイパス／外部スイッチャー ─────────→ projector
```

映像と音声は別入力です。登壇者PCのHDMIに会場マイク音声が含まれることを前提にしません。

## 試作で採用した技術候補

以下は本番確定ではありません。DroidKaigi後のレビュー、FlutterKaigi会場機材の実機試験、制作物チームのデザイン承認によって差し替えます。

### Flutter Web overlay

Flutterは字幕のレイアウトだけを担当します。ブラウザーのUVC権限、映像デバイス再接続、映像再エンコードを本線の故障点に加えないため、登壇者映像はOBSが扱います。Noto Sans JPをアプリへ同梱し、ネットワークなしでも同じ字体で描画します。

OBS Browser Sourceの1920×1080設定、字幕カードの位置・色・余白、1行64 pxは試作用の初期値です。実プロジェクターの最後列可読性、投影範囲、登壇スライドの安全領域を検証し、制作物チームが承認した値へ固定します。

### Dart local relay

同一PCの`127.0.0.1`で、静的ファイル、字幕投入API、WebSocketをまとめて提供します。ループバック以外へのbindは拒否し、字幕投入とclearにはURLへ載せない書込専用Bearer tokenを必須とします。ブラウザーのWebSocket読取は同一originに限定します。`flutter run`から確認する場合だけ、明示的な起動optionで別portのloopback originを一時許可できます。字幕はメモリ上にしか保持せず、本文・query・tokenをログへ出しません。新規接続時は期限内の最新字幕だけを再送します。

STT・翻訳ベンダーはリレーの外に置きます。これにより、翻訳APIの比較や来場者アプリ向けクラウドミラーが、正面スクリーンの表示契約を変えません。

### Caption Event v1

構造・型・基本制約の機械可読な正本は[JSON Schema](../../packages/caption_protocol/schema/caption-event-v1.schema.json)です。時刻の相対関係、表示時間上限、発話順序、前後空白・制御文字禁止などの意味制約はDartのprotocol実装とテストを正本とします。主なフィールド:

- `protocolVersion`: 現在は`1`
- `type`: `caption`、`clear`、`heartbeat`
- `roomId`／`sessionId`: 他会場・前セッションの字幕混入を防止
- `sequence`: 順序逆転や重複を破棄
- `utteranceId`／`utteranceSequence`／`revision`: 遅れて完了した古い発話・partialへの巻き戻りをrelayで拒否
- `translatedText`／`sourceText`／`isFinal`: 字幕内容
- `sourceStartedAt`／`producedAt`／`clearAt`: 発話開始からrelay受理までの遅延計測と、古い字幕の自動消去

来場者アプリへWebSocketやFirestoreで配信する場合も、このイベント形式を再利用します。ただしクラウドミラーはローカル表示から非同期に分岐し、失敗を本線へ伝播させません。

producerは発話区間の開始を`sourceStartedAt`としてUTCで記録し、同じ発話の全revisionで固定します。relayは受理したfinal字幕ごとに`relay受信時刻 - sourceStartedAt`を計算し、最新1,000件の数値だけからP50／P95／最大を返します。字幕本文、発話時刻の列、音声は測定用に永続化しません。この値は画面描画までのネットワーク・描画時間を含まないため、Go／No-Goでは実発話を撮影した映像による画面到達の確認も併用します。

### 表示チャンク契約

`translatedText`は1画面に収まる短い意味単位とし、STT・翻訳側が句読点や発話境界で分割して順番に送ります。オーバーレイの省略表示は安全弁であり、欠けた本文を自動で次画面へ送る仕組みではありません。文字数だけでは日本語・英語・混在文の幅を保証できないため、候補設定ごとのfixtureをプレビューと実プロジェクターで確認します。オペレーターは省略、意図しない改行、スライド重要領域との重なりを検知し、継続する場合は字幕を停止します。

## 障害時の原則

1. WebSocket切断・heartbeat停止・不正JSONでは、観客画面を無表示にする
2. 各字幕は`clearAt`で必ず消す
3. OBSに字幕なしシーンを用意する
4. 合成PCが停止しても使える物理バイパスを別系統で用意する
5. 本番投入の可否は、実会場試験と運営全体の承認後に決める

必須ゲートが1つでも未達なら、理由の種類を問わず正面スクリーン方式をNo-Goとし、来場者アプリ字幕へフォールバックします。

## 収録と配信の分離

会場投影と収録は別の出力として設計します。収録担当は次から選び、リハーサル前に信号経路を固定します。

- clean: 字幕なし映像のみを収録
- captioned: 字幕合成済み映像のみを収録
- both: cleanとcaptionedを別系統・別ファイルで収録
- post-production: cleanを収録し、編集時に字幕を付与

YouTubeの字幕は収録映像への焼き込みとは別ポリシーです。自動字幕、校正済み字幕、字幕なしのどれを公開するか、焼き込み字幕との重複を許容するかを配信・アクセシビリティ担当が別途承認します。
